come from a script anyone can rerun, with raw output saved. Put scripts in `tests/evaluation/` and

## 1. Analytics service: ingest, consumers, storage

- [ ] **Build** `POST /events/ingest` and Kafka consumers (group `analytics-consumers`) for every topic in [Tanya's guide step 1](tanya-guide.md#1-infra-docker-compose). Store envelopes, `trace.steps` records and dead letters in MongoDB.
- **Contract:** [Analytics & Logging Service](../api/data-contract.md#analytics--logging-service-owners-rohini-and-shashank).
  - **Valid envelope:** every field is required; an unknown `event_type` is rejected.
  - **Responses:** `202` on accept; `200` with `"duplicate": true` for a repeated `idempotency_key`; `400` for an invalid envelope, which is counted as a rejected envelope and written to the dead-letter list.
- **Mock reference:** `frontend/src/mocks/handlers/analytics.ts`. The UI already sends `property.viewed`, `search.performed` and `availability.notified`.
- **Done when:** with `VITE_ANALYTICS_API_BASE_URL` set, opening a property page creates a `property.viewed` document, and a malformed envelope sent by curl returns `400` and appears as a dead letter.
- **Needs:** T1–T2 (Kafka, MongoDB, `shared/`), T4 (real tokens).

## 7. Performance tests with JMeter (spec 9 and slide 5)

- [ ] **Log in first:** every JMeter script calls `POST /auth/login`, extracts `token`, and sends `Authorization: Bearer ${token}`. See the contract's "Performance tests" note in [Authentication and roles](../api/data-contract.md#authentication-and-roles-for-tanya-himja-rohini-and-shashank). Without it everything returns 401.
- [ ] **Dataset:** at least **10,000 records** (Tanya's generator, T14).
- [ ] **Spec 9 experiments:**

| Experiment | Measure |
|---|---|
| Property search | Throughput, average, p50, p95, p99, error rate, with rising concurrency |
| Booking request | End-to-end time from the API call (`202 processing`) through Kafka and the consumer to the database update (`pending` or `failed`): poll `/bookings/get`, or use the `processing → pending` status-history timestamps |
| AI debate | Time to first agent update, to challenge, to verdict, and WebSocket delivery latency |
| Kafka scaling | One consumer vs several consumers in a group |
| Indexing | Search with and without indexes (T14 scripts) |
| Failure recovery | Retry duration, duplicate prevention, dead-letter count, consistency after a consumer restart (T12) |
| Search strategies (13.8) | MySQL indexed vs Redis-cached search on the same workload: latency, throughput, memory, errors |

  The AI debate timings come from `ai_events` timestamps.
- [ ] **Slide 5 comparison: 100 simultaneous threads, four configurations, throughput bars with units:**
  - **B**: baseline (`USE_KAFKA=off`, `SEARCH_CACHE=off`, `SEMANTIC_CACHE=off`)
  - **B+S**: plus semantic caching (`SEMANTIC_CACHE=on`)
  - **B+S+K**: plus Kafka (`USE_KAFKA=on`)
  - **B+S+K+Other**: your own researched optimisation, e.g. Redis search cache (`SEARCH_CACHE=on`), database connection pooling, or more consumer instances.

  Use the same workload mix for all four (e.g. 70% search, 20% booking, 10% AI requests) and write down the machine, duration and dataset size.
- **Done when:** `.jmx` files are in `tests/performance/`, raw `.jtl` results and graphs in `docs/reports/`, and the report states which configuration the demo uses and why.
- **Needs:** T5–T12, T14 switches; H2–H8 and H11 for the AI parts.
